# 人物信息与角色面板重构

状态：隐私投影、场景名单、全局检索和玩家专属页签已接入运行时；完整发布验证见 [实施状态](../IMPLEMENTATION_STATUS.md)。

## 1. 面板应帮助玩家理解一个人

首屏回答四件事：这个人是谁，与我有什么牵连，我对他的了解从何而来，此刻能怎样接近或回应他。人物资料还承担交互入口和共同经历的回看；后台实体表不应决定玩家看到的栏目。

玩家自己的面板突出处境、本人明确的意图、义务、身体限制和可支配资源。NPC 的面板突出玩家已知的身份、相处经历、表达过的诉求与可接触方式。陌生人的面板可以只有外观、现场言行和自称。少量可靠内容也能构成完整页面。

## 2. 现状与必须移除的设计

当前 `src/components/Ck3CharacterWindow.tsx` 常驻身份与概览，下方默认进入“关系与家族”，其余页签是“健康与装备”“记忆与经历”“物品与资产”。这种排列让任何人物首先成为数值、家族与装备的集合，当前关系冲突和互动入口不够突出。

更严重的是独立记忆链：[characterDossier.ts](../../../src/features/characters/characterDossier.ts) 第 311 行复制 NPC 全量 memories；[CharacterHistoryTab.tsx](../../../src/components/character-window/CharacterHistoryTab.tsx) 第 133 行排序后在第 177 行起直接渲染。已有 worldEvents 可见性过滤不覆盖该链路。先在数据出口修复，再替换显示；不能把完整秘密传给组件后用 CSS 隐藏。

以下退出默认面板：NPC 全量内心记忆、精确隐性关系值、未经接触的特质图鉴、全知实时位置、远程人物完整装备与钱袋、面向所有对象的统一资产管理入口、同一装备在多个页签重复管理。原作资料转入明确的周目外参考入口；其信息不回灌角色认知。

## 3. 信息可见性矩阵

“公开”不等于玩家已经收到；起始社会知识必须由开局背景生成，并记录来源。可见性由观察者身份、取得信息的事件和当前时间共同决定。

| 信息 | 自己 | 熟人/有消息来源的 NPC | 初遇陌生人 |
|---|---|---|---|
| 名字与身份 | 当前身份、化名、已知社会地位 | 已知姓名/称谓；有争议时并列来源 | “披灰斗篷的使者”等可观察称呼；自称单独标注 |
| 年龄与出身 | 已设定资料 | 已知资料；不确定时“约四十岁” | 只展示确实可见的大致年龄；不自动补家谱 |
| 位置与存亡 | 自己所在场景与身体结果 | “三日前来信于白港”；死讯注明消息时间 | 当前现场可观察状态 |
| 能力 | 有证据的领域等级、限制、成长经历 | “曾统领守城”等经历推断；可信度措辞 | 现场动作与明显装备，不给六维精确值 |
| 性格 | 玩家确认的倾向及经历；不锁死选择 | “两次拒绝违誓”与具体事件；可有矛盾 | 当前表现，不生成终身人格判断 |
| 关系 | 已知制度关系、自身态度、互相表达过的立场 | 与自己的共同经历、已知亲属和义务 | 尚未建立关系；当前会面来源 |
| 目标 | 玩家亲自设定/确认；可修改、暂缓、放弃 | 对方表达的诉求或有来源的推断 | 对方当场提出的事情 |
| 记忆 | 亲历记录、收到的消息、玩家笔记 | 与自己有关且自己获知的经历 | 当前观察和介绍记录 |
| 伤势 | 自己已知症状、已确诊伤势、行动影响 | 可见症状或对方告知的诊断 | 明显外伤/行动异常，不暴露隐疾 |
| 物品与钱财 | 携带、托管与可调用资源明确区分 | 亲眼所见/获授权知晓的物件；传家宝传闻注明来源 | 看得见的物件，不能据此打开完整背包 |
| 秘密/私人欲望 | 本人的秘密及谁可能知道的有据判断 | 仅已获知的信息，保留泄露来源 | 不显示秘密数量、空槽、隐藏提示 |

自己也不是全知：未发现的疾病、暗中被调包的物品、他人是否知道自己的秘密，不能因为读取实体状态就自动确知。身体感受、检查诊断与引擎真实状态分层。

## 4. 新信息架构

**共用头部**：可见姓名/称呼、身份摘要、认识渠道、最近接触时间与地点。肖像遵守身份认知：对未知身份不能使用带真名说明的实名头像；无匹配资源时用中性占位，不假装其外貌已确定。

**默认“眼下”**：一条当前关系/处境摘要，两到四条确实相关的事情，一个主要接触动作。自己显示“待履行承诺、当前计划、身体限制”；熟人显示“正在讨论什么、上次留下什么、现在如何联系”；陌生人显示“你观察到什么、对方自称什么、可以怎样开口”。条数是排版上限，不是让模型补满的任务。

**“往事”**：共同经历、来往消息、玩家笔记；按时间排序，也可由当前争议跳到关键事件。每项区分发生时间、获知时间、消息来源、后续更正；文本可以展开正文锚点。玩家笔记始终标作个人判断，不直接改变世界事实。

**“关系”**：先显示与自己的关系，再按需要展开家属、效忠与共同利益。没有固定好感度百分比；用“曾为你担保”“正在追问失约原因”“婚姻关系仍成立”等有据描述。不同关系面向可以矛盾，例如亲近但不信任财务判断。对方未表达的真实态度只在受限的 NPC 决策上下文中存在。

**“身份与物件”**：已知头衔、经历、能力证据和可见物件。玩家自身提供随身物品管理；NPC 默认只读。获得管家、监护、搜查或借用权限后才出现相应操作，并说明权力来源与限制。选择一件物品进入单一详情，不在健康/装备/资产页重复编辑。

健康、完整家谱、领地和角色成长使用相关条目的专用详情。只有持续影响选择的内容在“眼下”置顶。页面入口可传 focusIntent，例如治疗入口直达伤势，正文名字入口默认眼下；不强迫用户每次从最顶层寻找。

## 5. 动作与面板的关系

| 处境 | 主动作 | 执行边界 |
|---|---|---|
| 同场且可交谈 | 与他交谈 | 填入带对象的行动草稿，玩家可改措辞 |
| 位置已知且存在通信渠道 | 写信 | 展示可用渠道、估计时效；寄出时才付出实际成本 |
| 只有旧消息 | 打听下落 | 以已知联系点开启调查，不瞬移到真实坐标 |
| 对方正在拒绝接见 | 托人引荐/说明来意 | 玩家选择接近方式，不默认凭身份强开对话 |
| 对方被拘押 | 探视/交涉 | 依据自己已知信息和权限提供尝试；审判与释放另有合同 |
| 收到死讯 | 查看消息/悼念 | 死讯可能不实；不能以是否存在“交谈”按钮泄露真实存亡 |
| 自己 | 整理打算/查看随身物品 | 写个人意图不消耗模拟时间；实际移动/治疗仍走行动事务 |

可尝试的社会行动与保证成功的系统操作分开建模。不能因为没有授权就禁止玩家说“我命令开门”；要允许提出要求，并由合法性、对方意愿与实力决定回应。无物理前提的“远程递物”则不能直接提交转移。

如果动作可用性本身依赖未获知的事实，界面只能给出基于当前认识的尝试，实际失败通过符合视角的事件解释。不得以按钮灰态、错误码或耗时差异提供精确秘密判断。

## 6. 数据合同与投影边界

下列是新类型草案，并非仓库现有导出。投影在组件和正文上下文的共同边界完成；原始 Character 数据不作为 UI 属性传入。

```ts
type KnownField<T> =
  | { status: 'known'; value: T; evidenceIds: string[]; learnedAt: string; observedAt: string }
  | { status: 'last_known'; value: T; evidenceIds: string[]; learnedAt: string; observedAt: string }
  | { status: 'unconfirmed'; claims: Array<{ value: T; evidenceIds: string[]; learnedAt: string }> }
  | { status: 'unavailable' };

interface CharacterViewRequest {
  runId: string;
  branchId: string;
  viewerId: string;
  subjectRef: string; // 可为未识别的会面对象引用，不能在可见标签中反查真名
  worldRevision: number;
  knowledgeRevision: number;
  asOfTime: string;
}

interface CharacterDossierView {
  subjectRef: string;
  identity: KnownField<{ displayName: string; description: string }>;
  whereabouts: KnownField<{ label: string }>;
  situation: string[]; // 每句必须由可见事实/有标记的个人推断形成
  evidence: VisibleEvidence[];
  relations: VisibleRelation[];
  actions: PerceivedAction[];
}
```

`VisibleEvidence`、`VisibleRelation`、`PerceivedAction` 应在实现时定义为受限投影，禁止夹带内部对象或秘密数量。`unavailable` 无 hiddenValue/secretCount。若 UI 无需展示字段，则省略整项，避免铺满“未知”。

规则上下文可拿裁决必要的隐藏事实；单个 NPC 决策只拿该 NPC 自己的知识；正文、可见选项与面板共用玩家视角投影。缓存至少包含以上 request 的全部影响字段以及投影版本；换角色、切周目、回档和异步返回时校验请求归属，禁止旧请求覆盖新面板。

认知更新由接触/观察/收到消息等事件触发，不因打开面板而发生。原作身份数据与剧情时间线不能成为“查过资料所以角色知道”的捷径。秘密过滤属于游戏体验边界；纯本地应用无法阻止玩家用开发工具读取本地世界数据，不将其宣传为防作弊安全隔离。

## 7. 关键交互状态

- 从正文点名字先给轻量人物预览；需要更多时扩展。桌面可固定到侧栏并继续阅读；手机进入完整详情页，返回恢复段落和草稿。
- 人物 A → 家属 B → 地点详情 → 返回，应依次恢复上下文。关闭详情与“返回自己”是两个不同动作。
- 当前页签和滚动位置按对象保存；玩家自己与陌生人不共享陈旧的页签内容。不能在加载期间闪现上一人物的秘密或身份。
- 局部资料未加载展示中性占位与重试；缺数据不能显示金币 0、死亡、无亲属等断言。已知旧信息可以继续展示，标注更新时间。
- 证据可折叠但必须通过点击、键盘和触控访问；不用仅 hover 可见的文字说明。正文信息使用 16–18px 起始候选，辅助文字至少 13–14px；以实际中文阅读测试定稿。
- 写信/交谈只预填草稿，普通面板导航不会发送。双击、触屏连点不会发起两个动作；异步处理中保留文本，失败能恢复。
- 玩家死亡后保留人物经历和关系，进入人生回顾、回到分支或新人生的明确流程。继承视角若未实现则不展示可用承诺。

## 8. 原型与验收

交互预览使用设计用示例人物与虚构会面内容，只演示“自己/熟人/陌生人”三种可见信息、四个分区、来源展开和动作草稿，不声称这些事件已发生于存档。原型没有接入模型或世界写入。

实现验收至少包括：

1. 私密记忆在 NPC 存储中存在，但不出现在玩家面板 ViewModel、DOM、无障碍文本或正文上下文；允许 NPC 自身决策读取。
2. A 告诉 B、B 未告诉玩家，玩家看 B 面板也不获知；消息实际到达后才可见。
3. 旧位置信息不跟随真实旅行自动变化；已知死讯为误报时，界面不会用隐藏的存活状态反证。
4. 同名与化名可正确导航；未知身份不从头像替代文本、链接标签、搜索结果泄露。
5. 自己的意图可编辑，NPC 诉求不可由玩家直接编辑；玩家记错的笔记不改变原事件。
6. 切换观察角色、读档或分支后，旧缓存和迟到请求不会污染面板。
7. 按键、触屏和 320px 宽屏都能访问主操作与证据；200% 缩放无关键内容裁切。
8. 可用性提示、物品数量、家谱节点、消息摘要和错误反馈都采用同一可见性边界。

这些作为 [UI/UX 总方案](ui-ux.md) 与 [阶段验收](validation-roadmap.md) 的人物专项门槛。

本次原型验证记录：19 项本地交互检查通过，涵盖三个观察对象、分区切换、草稿保留与可选设计控制；脚本无运行错误。Chrome 真实渲染检查了 736px 暗色、360px 亮色、320px 暗色，未发现横向溢出，且人工检查了截图。未完成真实游戏接线、软键盘与屏幕阅读器验证，因此不将这些原型结果计入产品发布通过率。

预览修订：用户报告宿主 MCP sandbox RPC 超时后，移除可选 Tweak 宿主控件连接，并将初始人物和分区正文写入静态首屏；所有交互只在本地 DOM 中运行。宿主 RPC 错误无法仅凭本地文件确定根因，因此此项属于减少宿主依赖及提供首屏降级，不宣称已修复应用侧服务故障。修订后的验证保留人物/分区/草稿检查，并用静态首屏与无宿主连接检查替代原设计控件检查。
