# 大量角色：分层模拟、登场与记忆

目标：保留世界中大量人物与真实关系，让玩家能长期扮演、结识新人、重逢旧人；模型调用和上下文随当前事情的复杂度增长，而不是随人物总数增长。状态：场景名单、相关人物召回、稀疏记忆和全局检索已接入；全局逐日 NPC 调度按设计暂缓，见 [实施状态](../IMPLEMENTATION_STATUS.md)。

人物地点、装备与其他领域的联动另见 [关联世界状态专项](linked-world-state.md)，重点是共享实体、派生位置、物品不重复生成和一次行动的完整提交。

## 1. 先分清三个数量

**世界资料里有多少人、这一周目改变过多少人、这一拍需要深入处理多少人，是三个不同的数字。** 不能为了控制提示词而删掉有意义的角色，也不能因为保留人物资料就每回合模拟其全部生活。

当前 [manifest.json](../../../public/data/agot-characters/manifest.json) 标明完整人物记录 2241 条，包含 canon 1397、semicanon 474、genealogy 370。这不是 2241 个同时存活/在场的角色。另有 1144 条 holderSummary，不能直接相加当成不同人物总数。

已有 [staticCharacterRepository.ts](../../../src/features/characters/staticCharacterRepository.ts) 使用搜索索引、人物/家系/装备分片与 Promise 缓存；[characterEventStore.ts](../../../src/features/characters/characterEventStore.ts) 的 Dexie 读取使用 `[runId+characterId]` 索引。这些基础可保留。后续应在事件索引、事务投影和候选来源上改进，不必从零重造人物数据库。

## 2. 四层人物与一层背景人群

层级表示本次需要多少模拟细节，不表示人物的重要性、社会地位或玩家可知程度。领主可能暂时是背景资料，守卫也可能成为最重要的朋友。

| 层级 | 什么时候属于这一层 | 保留和处理什么 | 模型开销 |
|---|---|---|---|
| 当前交互人物 | 正在与你对话、冲突、同行处置事件，或决定当前请求 | 身份、当前处境、诉求、可用资源、个人认知、相关经历；产生有依据的回应 | 正常场景模型覆盖；关键秘密决策按需单独处理 |
| 持续牵连人物 | 家人、伙伴、重要对手、未完承诺双方、正在替你办事的人 | 关系变化、未了事项、位置/通信/项目、关键记忆与下一处理时点 | 只有事件触发时需要；不每回合各调用一次 |
| 世界职能人物 | 某地领主、管家、学士、军需官等，目前与你无直接交互 | 真实身份与岗位、必要资源/权限、受相关事件影响的状态 | 通常由规则与事件推进 |
| 未激活人物 | 世界资料中存在，但没有进入本周目相关事件 | 静态基线与确已发生的动态覆盖，必要时按 ID 加载 | 默认零调用 |
| 未个体化人群 | 庭院守卫、街上行人、宴会宾客等背景集合 | 场所、职能、群体行为、观察范围；有需要再具名化 | 不逐人运行内心、背包和家谱 |

初始内容设计可围绕 2–6 位当前交互人物组织一场对话，持续牵连关系圈先用约 10–30 人验证体验；这是制作与测试的起点，不是硬性人口上限。没有理由时不强行塞满人物；多人法庭、宴会和战役允许更多参与者。

退回低层时不删除关系、承诺、伤势和经历，只停止无意义的高频处理。尚未到期的承诺可以不在上下文中，却必须继续有期限索引。强关系不意味着随时在玩家身边。

## 3. 人物何时被激活

激活必须有场景或事件依据：玩家直接接触、消息送达、承诺到期、组织事务影响其岗位、角色移动到相关场景、重要物件交接、关系变化或世界事件波及。

不能仅因模型“想让剧情精彩”就让某人瞬移登场，也不能因为玩家提及名字就认定那人听到了对话。

无名角色升级为稳定人物的触发：玩家询问身份或反复接触、对方收取/交出重要物品、双方发生承诺/冲突/关系变化、此人成为关键证人。先查询场景角色绑定，防止每次回到同一个岗亭都生成新的“那个守卫”。

稳定 ID 在具名之前就可存在；“北门值夜守卫”是玩家可见称呼，真实姓名未必已知。后续姓名揭晓只更新身份认知，不能创建第二个人。原作已有角色也不因初次遇见时不知道姓名而被重新生成。

高频普通采购或一次问路，可以只保存交易/信息事件及岗位来源；若后续需要追责或重逢，再依据既有事件绑定个体，不能随意改写原先谁说了什么。

## 4. 当前筛选器必须修正的接线

[sceneCharacterSelector.ts](../../../src/features/characters/sceneCharacterSelector.ts) 已有 12 张完整卡和轻量卡的概念，且允许被点名者/发言者超过 12 时保留。但 [worldTurnContext.ts](../../../src/features/world/worldTurnContext.ts) 随后又执行 `rawSelection.full.slice(0, 12)`，完整卡占满后 compactBudget 为零。外层二次裁切会破坏内层“强制保留”的约定。

该装配器目前从直接提及、强关系、近期参与者和未来原作事件参与者生成候选；没有把独立 Scene 的真实在场名单和当前发言者作为核心来源接入。之后又把直接提及/近期交互加入 presentCharacterIds。它同时存在“重要在场者可能没有进入候选”和“被提及的远方人物被视为在场”的方向相反的问题。

不能只把 12 改成 30。新入口先区分：

- `sceneParticipants`：全部已确认在场对象及进入/离开、可听可见范围。
- `actionTargets`：当前行动明确针对的人，可以在远方；需要符合通信/行动前提。
- `activeResponders`：本次实际需要回应的人。
- `referencedPeople`：被谈论或与事件有关的人，不因此获得在场权限。
- `backgroundGroups`：人群及岗位集合；不替代已具名的重要参与者。

先完成实体解析和必须满足的约束，再分配人物卡预算。发言者、行动目标、承诺双方与可能改变本次结果的参与者，其必要事实必须保留；普通背景可以只有一句角色描述。

必需内容超预算时，压缩卡片到当前动作必要字段，或将多人议程按实际发言顺序分拍处理；仍无法容纳就明确缩小本次处理范围，不静默漏掉关键人物后继续结算。公开向百人宣布决定时，可以对有据的听众集合记录同一发言，不要求模型为百人各写一句反应。

## 5. 候选检索与世界状态更新

候选不是从 2241 人中每拍让模型重新挑。先走轻量索引：稳定 ID/可见称呼 → 场景/岗位 → 当前事务参与者 → 未完事项 → 相关历史。对用户手选的人物 ID 优先使用明确引用；同名仍有歧义时保留多个候选，不能默认挑最著名的人。

读取順序：世界版本和场景 → 候选 ID 与必要关系边 → 对候选人物投影 → 按受众过滤 → 检索相关记忆 → 上下文预算编译。大量候选先用轻量索引排序，避免在截断前为每个人加载完整事件和装备。

实际关系存为稀疏、有类型的边，不给所有人物两两创建好感矩阵。血缘、婚姻、效忠保留已知基线；新关系只在有事件时形成。需要判断间接关系时做限定路径查询，不把整个家族树都塞给模型。

人物投影使用快照加快照之后的事件增量。快照/缓存键包含周目、分支、人物、源修订号和投影版本；读档、切分支、人物死亡或权限改变时精准失效。查询玩家面板另外包含观察者与认知版本。

## 6. 幕后人物会行动，但按事件推进

把需要继续发生的事情记录成持久化议程，例如“明早出发”“信使两日后抵达”“五日内偿债”“管家收到回信后再采购”。议程包含 actor、触发/到期时间、依赖条件、可用资源、当前步骤、失效条件、最近处理游标与来源。

模拟时间推进时取到期索引中的工作，按时间和依赖关系处理；无关人物不逐日扫描。例：玩家在书房聊十轮，若只过了半小时，远方使者不会因此走完十天路。

处理分级：日期推进、消息到达、正常路程按规则计算；普通事务使用条件模板；涉及性格冲突、重要让步或秘密抉择时，才调用必要的 NPC 决策。模板不适用时保留待裁定状态，不能猜一个会改变产权/婚姻/生死的结果。

同一批人物争抢同一资源时先预留并串行结算，不能各自基于旧快照成功。后台任务提交带幂等键与版本检查；玩家抢先改变条件则重新验证。并行读取可以使用，互相冲突的世界写入不能无条件并行。

事件很多时可以分批计算，但必须区分计算预算和游戏时间：影响即将进入场景的到期事件必须先处理完成；不能为了不卡顿就跳过截止日期，或把未计算的世界当作已经更新。恢复中展示简短状态，支持取消尚未提交的计算。

对没有建档的普通生活不补造详尽过去。人物重新相关时，根据已有基线、不可变历史和确已发生的事件恢复状态；允许补充此前未确定且不冲突的背景，但不能突然声称“你离开期间他早已结婚/杀人/出卖了你”来填空。

## 7. 几千人的记忆怎样保存

共享事件只保存一份权威记录，参与者、观察者和消息引用用索引连接。每人额外保存自己的理解、误解、态度与私人意图。不要把同一场宴会正文复制进一百个人的长篇记忆。

必须长期保留的锚点包括：身份与亲缘、婚约/誓言/债务、重大帮助与背叛、关键伤势、重要物件交接、秘密获知来源和未了事项。普通闲聊可归入有来源的阶段摘要，但不会覆盖锚点原文。

“记忆很多”不等于每拍全读。为当前话题取相关事件、最近相处和未完事项；自己记得过去并不代表一定每次主动提起。重逢时召回关键经历，不要求 NPC 把旧剧情复述一遍。

知情关系严格使用事件发生时的受众快照及后续传播事件。某人后来加入家族，不自动获得家族全部旧秘密；群组受众不能按今日成员名单反推过去。规则可读必要真实状态，NPC 决策只读本人认知，玩家正文和人物列表只读玩家获知的部分。

无需默认为每个 NPC 配一个常驻模型或独立代理。模型在需要判断时获得该人的状态切片，输出受规则限制的行为提案；持久的人格和记忆存在游戏数据中。

## 8. 多人场景怎样写得清楚

百人宴会可以记录实际听众范围，正文只聚焦玩家关注的几个人。发言依话题、身份、轮次和是否被点名发生，不机械让每人轮流插话。

先确定各相关人物的可见行动，再统一写一段正文，避免分开生成后出现同时抢话、场地位置冲突或某人知道了没听见的话。关键人物有独立秘密时按已有隔离协议先得出安全行为计划，正文不读取秘密原因。

每位长期交互人物建立少量可验证区别：想得到什么、不能轻易放弃什么、常用表达方式、如何看待玩家以及形成这种态度的事件。不要靠口癖、称号或一长串特质标签假装人物不同。性格允许随重大经历变化，有事件依据；不能每次重新抽样人格。

## 9. 大量角色的 UI

人物入口默认分为：眼前的人、与你有未完事项的人、熟识的人；搜索可查询角色背景支持的已知公共人物、已有称谓和收到的消息。普通游戏不默认铺满原作全人物库。

列表只显示已知姓名/称谓、与你的牵连、最后接触或消息时间。不要在列表上暴露未获知的死讯、位置、敌意或当前私密任务。后台活跃层级属于引擎内部，不用“休眠人物”之类标签破坏游戏视角。

分页/虚拟列表用于长名单，人物卡片只在进入可视区或点开后加载必要资源。搜索与打开面板不会推进模拟时间、改变关系或让对方知道被查询。

家谱按近亲与局部展开，远支按需加载；人物网络默认展示与当前事情相关的一小部分。曾经重要但已失联的人保留记录，不因不活跃而从手记中消失。原作百科与调试全知列表继续放在周目外边界。

## 10. 验收与实施顺序

先修正当前双重裁切和在场误判，再接入场景名单/行为对象，随后实施未了事项索引、按事件调度、人物快照与稀疏认知。最后才依据测量增加检索服务或更复杂后台模拟。

必需场景：

1. 现有 2241 条资料与扩容到一万条合成资料时，同样的两人会面产生相同必要上下文；输入大小不随数据库线性增长。
2. 十三个被点名对象不因两层截断丢失；百人听众的发言受众与实际生成反应的焦点人物分开。
3. 在场但未被提及的证人仍能参与事件；谈到远方领主不会让他在场、听见或直接收物。
4. 同一个无名守卫重逢保持身份；具名不创建副本，同名人物不串台。
5. 伙伴离场二十回合后重逢仍记得承诺；闲聊轮数不会加速旅行，世界日期推进则正确处理到期事项。
6. 多个后台任务争用同一封信/马匹只会合法分配一次；崩溃重试不重复送达或支付。
7. 新加入组织的人不知道加入前的秘密；列表、搜索、家谱、地图与正文一致过滤认知。
8. 分支 A 的人物变化不进入分支 B；快照恢复与原事件回放产生一致结果。

先记录当前候选检索耗时、读取事件数、投影耗时、输入 tokens、NPC 决策调用数和长列表响应，再定性能门槛。测试一万条只用于扩容压力，不等于已完成一万个独立人物的内容制作。

结论：角色总数可以大；每次深入思考的范围要小且完整。人物离开镜头后，仍保留身份、关系和待发生的事。
