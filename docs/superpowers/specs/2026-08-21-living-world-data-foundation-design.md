# 活世界数据基础与硬编码收敛设计

日期：2026-08-21  
状态：待确认

## 1. 目标

本项目的最终方向是一个以 298 AC 固定时点开始、能够持续演化的维斯特洛人物沙盘。玩家选择控制人物只是选择观察与行动视角，不会进入不同剧本，也不会复制出多套世界。

本阶段先解决阻碍后续世界模拟的内容硬编码问题：将世界起点、可玩人物、人物叙事资料、共享术语、普通物品和 NPC 初始装备从运行时代码中分离，并缩减没有游戏职责的 AGOT 模组填充人物与过细地点语义。

本阶段不实现完整 NPC 自主行动循环，但产出的数据边界必须能够直接供后续“世界脉冲”模拟器使用，不能演变成另一套线性剧情系统。

## 2. 核心原则

### 2.1 只有一个世界

- 世界 ID 唯一。
- 开始时间固定为 298 AC 5 月 10 日。
- 所有人物、头衔、地点和资产共享同一份初始状态。
- 玩家选择奈德、琼恩、丹妮莉丝或未来开放的其他人物时，只改变玩家控制主体和知识视角。
- 不创建 `scenarios/`、任务线或人物专属世界副本。
- 现有 `scenarioId` 仅作为旧存档元数据兼容字段保留，不再作为新架构概念扩展。

### 2.2 内容数据化不等于规则数据化

应迁出代码的内容：

- 固定世界日期和初始世界事实；
- 可玩人物名单及视角引导；
- 人物叙事补充；
- 人物开局位置与活动；
- 初始资产、保管和装备；
- 普通物品声明；
- NPC 装备模板和人物覆盖；
- 文化、信仰、关系等共享显示词典；
- 哪些地点具备玩家可见的游戏语义。

继续留在代码中的规则：

- 存档格式和 Schema；
- D20、装备、容量、旅行和伤势算法；
- 人物命令、世界事务与权限校验；
- 知识可见性和消息传播规则；
- 地图缩放、渲染与坐标算法；
- 世界状态合并顺序；
- 原子提交和回滚；
- UI 组件布局与稳定界面文案。

### 2.3 数据库规模不等于模拟规模

AGOT 导入资料是参考数据库，不是每回合运行名单。当前运行时人物数据包含 11,450 人，其中：

- `canon`：1,397；
- `semicanon`：474；
- `mod_supporting`：8,430；
- `genealogy`：1,149。

后续必须区分：

1. **档案人物**：只供查询、亲属和历史引用；
2. **世界人物**：在固定起点存在，可被事件激活；
3. **活跃人物**：当前参与场景、计划或世界脉冲；
4. **临时背景角色**：尚未成为持久实体的守卫、仆役、商人等群体描述。

只有活跃人物进入高成本模拟和 LLM 上下文。

## 3. 当前主要问题

### 3.1 固定起点散落在代码中

`src/data/presets.ts` 同时保存人物选择卡、重复人物资料、属性、物品、地点、长篇开场正文和分支。`src/features/world/characterWorldFacts.ts` 又单独保存 `OPENING_CHARACTER_LOCATIONS`。同一固定世界的事实被按玩家入口拆成多套代码对象。

### 3.2 角色面板来源分散

人物面板当前组合：

- AGOT 人物分片；
- 家族手写表；
- 人物叙事补充生成文件；
- 开局位置硬编码；
- 文化与信仰映射；
- 关系称谓映射；
- 当前存档事件；
- 资产和装备投影。

动态投影逻辑是正确方向，但内容来源没有统一边界，增加人物或修正资料时需要修改多个 TypeScript 文件。

### 3.3 模组填充人物过多

8,430 名 `mod_supporting` 中，当前静态分析显示约 5,553 人没有现任头衔、核心人物一层亲属、神器或人工内容引用。这些人物对当前产品没有明确职责，却扩大搜索、装备生成和维护范围。

不能直接删除全部 `mod_supporting`：其中约 1,141 人是当前头衔持有人，约 1,839 人是原作或半原作在世人物的一层亲属，12 人参与神器初始归属；这些集合存在重叠。

### 3.4 地图视觉粒度被误当作内容粒度

当前地图有 6,094 个省份/地点记录、1,077 个伯爵领和 31,724 条路线边。高精度几何对渲染、归属和寻路有价值，但并非每个省份都应成为需要人物、描述、资产和事件的可玩地点。

## 4. 统一世界内容结构

所有人工维护内容归入一个世界命名空间；物理分文件仅服务于维护和按需加载，不代表多个世界或剧本。

```text
content/world/
├── manifest.json
├── playable-characters.json
├── start-state/
│   ├── characters.json
│   ├── titles.json
│   └── assets.json
├── characters/
│   ├── agot_Stark_3.json
│   └── ...仅有人工增强内容的人物
├── items/
│   ├── ordinary-items.json
│   ├── loadout-templates.json
│   └── loadout-overrides.json
├── locations/
│   └── gameplay-locations.json
└── terminology/
    ├── cultures.json
    ├── faiths.json
    └── relationships.json
```

这些是编辑源。运行时不直接遍历源目录，而由编译器校验并生成确定性的索引或分片。

### 4.1 世界清单

`manifest.json` 只声明唯一世界和数据依赖：

```json
{
  "schemaVersion": 1,
  "worldId": "agot-298",
  "startDate": { "year": 298, "month": 5, "day": 10 },
  "characterDataset": "agot-characters",
  "mapDataset": "agot-map",
  "artifactDataset": "agot-artifacts"
}
```

固定日期不得再分散写在人物预设、世界投影和测试 fixture 中。测试可以构造其他日期验证算法，但产品新世界入口只使用该清单日期。

### 4.2 可玩人物

`playable-characters.json` 只保存视角资格和入口展示所需的少量内容：

```json
[
  {
    "characterId": "agot:Stark_3",
    "enabled": true,
    "difficulty": "normal",
    "focus": ["王室御驾抵达临冬城", "保护家族与北境"]
  }
]
```

姓名、年龄、家族、头衔、属性、特质、地点和装备不得在此重复；全部从人物基础资料和统一起点状态解析。

`focus` 只是人物当下关注点，不是任务、胜利条件、强制事件链或预写剧情。

### 4.3 世界初始状态

`start-state` 保存 298 AC 5 月 10 日这一刻的可变事实基线：

- 人物实际位置和当前活动；
- 需要覆盖导入资料的生死或伤势；
- 头衔当前持有人和实际控制例外；
- 唯一资产的位置、所有权和保管关系；
- 普通物品的必要初始实例；
- 已经成立的公开世界事实。

所有玩家视角从同一个起点初始化。选择人物不得改变其他人物的位置、资产或头衔。

### 4.4 人物内容文件

不为 11,450 人创建文件。只有需要人工增强的人物才有一个 JSON；当前约 113 名已有卷宗补充的人物可作为首批迁移范围。

人物文件只保存导入资料无法可靠提供的叙事内容：

```json
{
  "schemaVersion": 1,
  "characterId": "agot:Stark_3",
  "summary": "……",
  "aliases": ["奈德"],
  "appearance": "……",
  "personality": "……",
  "reputation": "……",
  "publicRoles": ["北境守护"],
  "notableRelations": [],
  "experiences": [],
  "sources": []
}
```

禁止在人物内容文件中重复：

- 基础姓名、性别和出生日期；
- 当前年龄或在世状态；
- 当前地点；
- 当前装备和资产；
- 当前头衔；
- 游戏开始后产生的关系、经历、记忆和目标状态。

开局位置属于统一 `start-state`，不写进人物简介文件。运行时变化只写入存档事件和稀疏覆盖，绝不反写源 JSON。

## 5. 角色面板投影

角色面板继续是动态投影，不改成“直接渲染 JSON”。统一合并顺序为：

```text
AGOT 人物基础记录
→ 可选人物叙事内容
→ 固定世界初始状态
→ 当前存档人物事件与世界事件
→ 当前玩家知识过滤
→ CharacterDossier ViewModel
→ 角色面板
```

各区域权威来源如下：

- 姓名、性别、出生、家族和基础亲属：AGOT 人物资料；
- 简介、别名、外貌、性格、声誉和人工经历：人物内容文件；
- 298 AC 初始位置、活动、伤势：统一世界初始状态；
- 当前地点、生死、关系、头衔、伤势和记忆：运行时事件；
- 装备和资产：统一物品/世界资产状态；
- 文化、信仰和关系名称：共享术语表；
- 可见内容：知识过滤后的投影结果。

“关系与家族”“健康与装备”等页签名称和按钮文本属于 UI，不进入人物数据。

没有人物内容文件时，角色面板仍必须能用 AGOT 基础资料正常展示；不能显示虚构补全，也不能把缺少人工简介视作错误。

## 6. 人物裁剪与分级

### 6.1 完整保留

运行时人物档案完整保留：

- `canon`；
- `semicanon`；
- 可玩人物；
- 有人工人物内容者；
- 固定世界起点显式引用者；
- 神器或重要资产持有人；
- 上述人物为保持可见亲属关系所需的一层亲属。

### 6.2 头衔持有人摘要

不重要但持有头衔的 `mod_supporting` 不必自动成为完整世界人物。编译器可将其投影为轻量持有人摘要：

- 稳定人物 ID；
- 姓名；
- 家族/宗族 ID；
- 生死状态；
- 当前头衔 ID；
- 必要的显示标签。

地图和头衔详情可以使用摘要，不要求为每个低级领主生成完整装备、目标、记忆和角色面板内容。

若玩家与摘要人物产生直接互动，系统可从保留的导入档案确定性地实体化为当前存档人物；实体化后使用稳定 ID，并持续保存其事件和状态。

### 6.3 删除范围

导入器和裁剪器应排除：

- 无任何正式引用的 `mod_supporting`；
- 不连接到保留人物的 `genealogy`；
- `technical`、dummy 和 placeholder；
- 随被排除人物产生、且没有其他用途的装备分配记录；
- 只为填充人口而存在、没有头衔、亲属、资产或内容职责的记录。

根据当前数据，第一轮候选至少包括约 5,553 名无引用 `mod_supporting` 和约 799 名无引用 `genealogy`。最终数量必须由可复现的引用闭包计算产生，不能把这些盘点数字写成不可变规则。

### 6.4 搜索与模拟

- 默认人物搜索优先并默认限制于 `canon`、`semicanon` 和已实体化人物；
- 持有人摘要只在对应头衔或地点上下文中出现；
- 族谱辅助人物仅在查看相关族谱时按需提供；
- 世界脉冲不遍历全部档案人物；
- LLM 上下文只包含当前活跃人物和明确相关人物。

## 7. 地图语义收敛

### 7.1 视觉省份

保留全部 6,094 个省份几何，用于：

- 地形、海岸线和边界；
- 政治着色；
- 像素命中与空间归属；
- 路径基础数据。

视觉省份不是内容实体，不需要描述、人物、资产、经济或独立事件。

### 7.2 政治单位

五级头衔继续保留：

```text
霸权 → 帝国 → 王国 → 公国 → 伯爵领
```

所有边界和名称可以显示，但不要求每个伯爵领都进行完整模拟。背景领地可以只提供名称、层级、持有人摘要和控制状态。

### 7.3 旅行节点

路线图允许存在不可见的中转节点。中转节点只参与路径计算，不进入：

- 地点搜索；
- 角色面板地点链接；
- 资产落点选择；
- LLM 地点候选；
- 地点详情页。

### 7.4 游戏地点

`gameplay-locations.json` 定义真正具备游戏语义的地点，来源必须满足至少一项：

- 著名城堡、城市、城镇、港口、遗迹或地标；
- 固定世界人物或资产的起点；
- 政治中心；
- 重要路线入口、渡口或港口；
- 已有正式世界事件明确引用。

只有游戏地点可以：

- 被搜索和选中；
- 成为人物或资产的权威位置；
- 出现在角色面板和正文实体链接中；
- 承载地点详情和本地场景；
- 被世界模拟器选为行动目标。

城堡大厅、卧室、神木林和码头区等继续使用 `sceneLocation` 表达，不新增地图实体。

首轮不强制人工达到某个地点数量。编译器先根据上述规则自动生成候选，再通过显式允许/排除表校正；目标是把可玩地点控制在数百级，而不是 6,094 个。

## 8. 普通物品与 NPC 装备

`itemDefinitions.ts` 中声明式普通物品、NPC 装备模板和人物覆盖应迁入世界内容源。代码继续拥有：

- 物品 Schema；
- 效果种类和执行器；
- 装备兼容性规则；
- 容量、转移、损坏和使用算法；
- 唯一物品约束。

数据文件只声明已经注册的效果类型和参数。未知效果类型、非法装备位置、重复物品 ID、悬空人物 ID 或唯一资产重复必须在编译阶段失败。

AGOT 神器继续由现有离线导入管线生成，不与手写普通物品混为同一来源。

## 9. 编译产物与运行时加载

新增世界内容编译器，将 `content/world` 与现有 AGOT 静态资料交叉校验，输出版本化运行时数据：

```text
public/data/world/
├── manifest.json
├── start-state.json
├── playable-characters.json
├── character-content/
├── terminology.json
├── gameplay-locations.json
└── holder-summaries.json
```

要求：

- 输出顺序稳定、哈希可复现；
- 构建失败保留上一份完整产物；
- 不在浏览器中编译源内容；
- 不访问网络、Steam 或 Workshop；
- 大型人物基础数据继续按哈希分片加载；
- 人物内容可以按人物 ID 分片或合并为少量分片，不能产生上万个运行时请求；
- 世界 manifest 记录人物、地图、神器和内容产物哈希，阻止互不匹配的数据组合。

## 10. 为活世界预留的边界

本阶段只建立数据基础，不立即实现以下模拟逻辑，但数据模型不得阻碍后续加入：

- 势力议程；
- 人物长期目标；
- 地区压力；
- 人物行动候选；
- 消息传播；
- 活跃人物集合；
- 背景世界的抽象推进。

未来世界脉冲必须消费统一世界状态，并通过现有人物命令、资产命令、头衔规则和旅行规则产生已验证事件。LLM 可以参与候选选择和叙事表达，但不是世界状态权威。

人物内容中的性格与目标只能作为决策输入，不能写成强制触发的预定剧情。

## 11. 迁移顺序

### 阶段一：唯一世界入口

- 建立 `content/world/manifest.json`；
- 固定唯一开始日期；
- 将三个“预设场景”改为三个可玩人物入口；
- 删除重复的人物姓名、年龄、家族、属性、特质和地点声明；
- 将长篇预写开场与固定分支从世界初始化职责中移除；
- 保持现有存档格式 9，旧存档仍能读取。

### 阶段二：起点状态与角色面板内容

- 迁移 `OPENING_CHARACTER_LOCATIONS`；
- 迁移初始活动、伤势、装备和资产；
- 将现有约 113 名人物补充资料转换为单人物编辑文件；
- 集中文化、信仰和关系显示词典；
- 角色面板改为统一投影顺序。

### 阶段三：人物和地图裁剪

- 由引用闭包裁剪无职责模组人物；
- 为背景头衔持有人生成摘要；
- 区分视觉省份、隐藏中转节点和游戏地点；
- 默认搜索与 LLM 上下文不再包含无意义填充实体。

### 阶段四：物品内容迁移

- 迁移普通物品声明；
- 迁移 NPC 装备模板与重点人物覆盖；
- 保持现有效果执行和资产权威关系不变。

完成这些阶段后，再单独设计和实现世界脉冲，而不是在数据迁移中顺便加入未经验证的 NPC AI。

## 12. 兼容与迁移约束

- `saveFormatVersion` 保持 9；
- 地图 manifest `schemaVersion` 保持 4；
- 不删除正式地图几何、瓦片、地形和五级头衔数据；
- 不改变现有稳定人物、地点、头衔和资产 ID；
- 已有存档中的人物和地点引用必须继续解析；
- 被从默认资料库裁掉、但已出现在旧存档中的人物必须通过存档快照或兼容档案解析，不能导致存档损坏；
- 玩家可见人物事实不得因数据迁移发生无依据变化；
- 不在此阶段改动地图视觉、角色面板布局或玩法规则；
- 不提高首屏 750 KiB JavaScript 预算；
- 不创建 worktree；
- 不推送远端。

## 13. 校验与测试

至少新增以下自动校验：

1. 世界 manifest 唯一且开始日期固定为 298-05-10；
2. 可玩人物全部存在、在起始日期已出生且可用；
3. 可玩人物名单不重复基础人物事实；
4. 起点人物位置全部指向游戏地点；
5. 人物内容文件 ID 唯一，并与 AGOT 人物身份一致；
6. 人物内容不包含当前年龄、当前生死、当前头衔、当前装备等运行时字段；
7. 文化、信仰和关系词典键无重复；
8. 裁剪后所有亲属、头衔、神器和人工内容引用均可解析；
9. 无引用模组人物不会进入默认运行时人物索引；
10. 头衔持有人摘要覆盖被降级但仍在位的领主；
11. 游戏地点全部具有有效地图坐标和层级；
12. 隐藏中转节点不可搜索、不可成为人物或资产位置，但路线仍可经过；
13. 角色面板在无人工内容时仍正常展示基础资料；
14. 角色面板中的死亡、地点、关系、装备和资产仍由当前存档覆盖；
15. 现有三个玩家入口从同一世界起点创建状态；
16. 切换玩家入口不会改变非玩家人物的初始世界事实；
17. 旧版本 9 存档继续恢复；
18. 全量验证、地图验证、世界闭环验证、包体检查和生产构建通过。

## 14. 验收标准

本阶段完成时应满足：

- 产品概念中不存在多个剧本，只有一个固定起点世界；
- 角色选择只是玩家视角选择；
- `presets.ts` 不再保存完整人物和长篇开场世界副本；
- `characterWorldFacts.ts` 不再保存人物开局位置表；
- 人物面板的人工叙事内容可在独立人物文件中维护；
- 不要求为所有 AGOT 人物建立人工 JSON；
- 无职责模组填充人物从默认运行时资料中移除；
- 背景领主可以轻量摘要存在，不会导致地图大面积丢失持有人；
- 6,094 个省份继续支撑视觉和空间计算，但不再等同于 6,094 个可玩地点；
- 普通物品和 NPC 初始装备不再依赖巨型手写 TypeScript 内容表；
- 运行时动态变化仍由已验证命令、事件和存档控制；
- 数据结构可以直接支持后续活跃人物、势力议程和世界脉冲设计。

## 15. 非目标

本阶段明确不做：

- 多剧本或任务线系统；
- 为地图填充虚构人物；
- 为每个省份、伯爵领或人物补写内容；
- 删除地图高精度视觉数据；
- 每回合模拟全部人物或全部领地；
- 新增经济、人口、军队或建设系统；
- 实现完整世界脉冲；
- 让 LLM 直接决定或写入未经验证的世界状态；
- 改版地图、人物窗口或资产界面视觉。

## 16. 后续阶段

本数据基础稳定后，下一份独立规格将设计“活世界脉冲”：

```text
时间推进
→ 更新地区与势力压力
→ 选择有限活跃人物
→ 生成合法行动候选
→ 规则验证与确定性结算
→ 写入世界事件
→ 通过消息传播决定玩家何时得知
→ 正文、地图、人物与资产重新投影
```

其验收核心是：即使玩家选择等待，世界中的相关人物与势力也会产生合法、持久、可被发现且能够被玩家干预的变化。
